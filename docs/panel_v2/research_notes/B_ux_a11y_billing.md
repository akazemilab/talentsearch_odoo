### B1
Verdict: CORRECTED (claim is right on the SC list but wrongly implies all six are "AA" - two are Level A)
Sources fetched: https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/ ; https://www.w3.org/TR/WCAG22/ ; Understanding docs: target-size-minimum, focus-not-obscured-minimum, consistent-help, redundant-entry, dragging-movements, accessible-authentication-minimum ; https://www.w3.org/WAI/standards-guidelines/wcag/ ; https://www.wcag22aa.org/new-criteria/ (NOT official W3C: "maintained by Sonoma Solutions ... independent educational resource")
Levels (all confirmed on W3C new-in-22):
- 2.4.11 Focus Not Obscured (Minimum) - AA. "the component is not entirely hidden due to author-created content."
- 2.4.12 Focus Not Obscured (Enhanced) - AAA. No part of focused component hidden.
- 2.4.13 Focus Appearance - AAA. Indicator >= area of 2 CSS px thick perimeter and 3:1 contrast focused vs unfocused.
- 2.5.7 Dragging Movements - AA. "can be achieved by a single pointer without dragging, unless dragging is essential" (or UA-determined).
- 2.5.8 Target Size (Minimum) - AA. "at least 24 by 24 CSS pixels", five exceptions: Spacing (24px-diameter circle centred on each undersized target's bounding box must not intersect another target/its circle), Equivalent (same function via another control on same page that meets the SC), Inline (target in a sentence or constrained by line-height of non-target text), User agent control (size set by UA, not modified by author), Essential (particular presentation essential or legally required).
- 3.2.6 Consistent Help - Level A. Help mechanisms (human contact details, human contact mechanism, self-help option, fully automated contact mechanism e.g. chatbot) repeated across pages "occur in the same order relative to other page content".
- 3.3.7 Redundant Entry - Level A. Info previously entered/provided in same process is "auto-populated, or available for the user to select". Exceptions: essential, security (e.g. password confirmation), no longer valid.
- 3.3.8 Accessible Authentication (Minimum) - AA.
- 3.3.9 Accessible Authentication (Enhanced) - AAA (stricter: removes the object-recognition and personal-content exceptions).
Exact count: 9 new SCs; 6 are A/AA (2.4.11 AA, 2.5.7 AA, 2.5.8 AA, 3.2.6 A, 3.3.7 A, 3.3.8 AA); 3 are AAA (2.4.12, 2.4.13, 3.3.9). So "WCAG 2.2 AA includes ..." is correct as conformance scope (AA conformance requires A+AA), but write the spec as "2.2 AA conformance = these 6 new A/AA SCs"; 3.2.6 and 3.3.7 are Level A.
3.3.8 and SMS OTP (Understanding doc): "A service that requires manual transcription of a verification code is not compliant." Cognitive function test defined as "A task that requires the user to remember, manipulate, or transcribe information." Copy/paste & password managers OK: "Copy and paste can be relied on to avoid transcription." Also "Blocking people from pasting into authentication fields...would force the user to transcribe information". So: yes, transcribing is a cognitive function test; an OTP field passes only because paste/autofill works (mechanism-to-assist exception). Email-link auth listed as a sufficient technique (G218). Also the doc says the code may be pasted "from ... text message application" - i.e. allow paste; autocomplete="one-time-code" is the practical enabler.
Removed: 4.1.1 Parsing. TR: "WCAG 2.2 has removed one success criterion, 4.1.1 Parsing."
Status: W3C Recommendation 5 Oct 2023, updated 12 Dec 2024. W3C: 2.2 "does not deprecate or supersede WCAG 2.1"; content conforming to 2.2 also conforms to 2.1 and 2.0.
ISO: W3C news 2025-10-21 https://www.w3.org/WAI/news/2025-10-21/wcag22-iso/ : "WCAG 2.2 is now an approved ... (ISO) standard: ISO/IEC 40500:2025." (iso.org/standard/91029.html listing: edition 2, published September 2025; that page summary also mentioned a further revision "ISO/IEC DIS 40500" in development - only seen through summariser, treat as unverified.)
WCAG 3 as of 2026: https://www.w3.org/TR/wcag-3.0/ is a W3C Working Draft dated 10 September 2026; "does not deprecate WCAG 2"; "inappropriate to cite this document as other than a work in progress." Not a Recommendation; design to WCAG 2.2 AA.
Newer: WCAG 3 WD 10 Sep 2026 (APCA-style contrast etc. is draft only); ISO adoption makes 2.2 formally citable in procurement.

### B2
Verdict: CONFIRMED (NN/g) / CORRECTED-detail (Carbon taxonomy is three types, not four)
Sources: https://www.nngroup.com/articles/empty-state-interface-design/ ; https://carbondesignsystem.com/patterns/empty-states-pattern/
NN/g three guidelines: (1) Communicate system status: "increase the visibility of system status". (2) Learnability: "Tell the user what could be displayed, and how to populate the area with that content." (3) Direct pathways: "Provide direct pathways (i.e., links) to getting started with key tasks".
Carbon taxonomy: (1) No data - "First time use, no data yet"; (2) User action - result of a user action, e.g. "no search results" or task-completion; (3) Error management - "there is data but it cannot be surfaced": permissions ("The user does not have permission to view the data"), systems issues, configuration required, unsupported actions (e.g. unsupported file upload). Supplementary first-use aids: in-line documentation, onboarding, starter content. So "no permission" is a sub-case of Error, not a top-level type.
Newer: none found.

### B3
Verdict: PARTLY (primary M3/M2 pages NOT fetchable; M1 primary fetched; Material also isn't RTL-Persian-specific)
Sources fetched: https://m1.material.io/usability/bidirectionality.html (OK); https://www.mdui.org/en/design/1/usability/bidirectionality.html (unofficial mirror of M1, same content); m2/m3.material.io - could not render. https://learn.microsoft.com/en-us/globalization/fonts-layout/mirroring (thin); https://www.w3.org/TR/alreq/ ; https://www.w3.org/International/questions/qa-html-dir
Mirrored (M1): directional icons ("Icons that communicate direction, like arrows, are mirrored"), text-field icons on opposite side, navigation buttons in reverse order, text right-aligned, progress bars (fill right-to-left: "0% on the right"), timelines/sequence of events progress right to left.
NOT mirrored (M1): "Icons that do not communicate direction, such as a camera"; "Numbers, such as the clock and phone numbers"; "Charts and graphs"; untranslated text. Media playback: from the first M1 fetch, "Do not mirror media playback buttons and the media progress indicator" and "Clocks still turn clockwise" (summariser output; re-verify before quoting). Checkmarks are not listed in what I could read (treat as non-directional = not mirrored; unverified).
Be exact: charts/graphs NOT mirrored (but axis labels/legend text are text and flow RTL; do not flip data axes - time axes left-to-right is the common practice but M1 says only "charts and graphs" not mirrored); progress bars and step/timeline UIs ARE mirrored; media scrubber NOT mirrored.
Microsoft Learn: only "fast-forward and rewind icons in media players, use the same orientation in both LTR and RTL".
W3C alreq: three digit families: European 0-9; Arabic-Indic ٠-٩ (Egypt, Saudi, Iraq); Eastern Arabic-Indic (Persian) ۰-۹ "used in Iran and Afghanistan". Bidi: "European digits and Eastern Arabic-Indic digits are of category EN ... Arabic-Indic digits are of category AN" - so Persian and Latin digits behave the same in UBA; mixing ٥ (Arabic) vs ۵ (Persian) changes ordering. Phone numbers/quantities need particular attention to symbol placement/spacing. Don't use Arabic-Indic digits in Persian UI (4/5/6 differ visually: ۴ ۵ ۶ vs ٤ ٥ ٦) and normalise on input.
W3C i18n qa-html-dir: `dir="rtl"` on <html>; `dir="auto"` on inputs/forms; phone/email: wrap in `<bdi>` or set `dir="ltr"`; example `<input type="tel" name="phone" dir="ltr">`; use logical CSS (start/end); `dirname` attribute optional. HTML spec: autocomplete="one-time-code" is a valid autofill field name (control group Password; free-form text).
Recommended markup for LTR runs in RTL forms: `<input type="tel" dir="ltr" inputmode="numeric" autocomplete="tel">` ; OTP `<input type="text" dir="ltr" inputmode="numeric" autocomplete="one-time-code" pattern="[0-9]*">` (+ accept Persian/Arabic digits server-side/JS normalisation); email `dir="ltr"` or dir=auto; display phone/IDs in tables with `<bdi>`/`dir="ltr"` + `unicode-bidi:isolate`.
Newer: M3 page contents unknown - tell the prompt author to re-verify on a machine that can render m3.material.io.

### B5
Verdict: PARTLY (most claims supported, three need correction: one wallet per customer; per-grant expiry; consumption priority)
Sources: https://getlago.com/blog/prepaid-credit-api-implementation-guide ; https://getlago.com/docs/guide/wallet-and-prepaid-credits/overview (doc.getlago.com redirects here) ; wallet-top-up-and-void ; api-reference/wallets/{create,get-all-transactions,get-all-consumptions} ; https://getlago.com/docs/guide/events/ingesting-usage ; https://flexprice.io/blog/how-to-implement-credit-based-billing-for-ai-applications ; https://docs.stripe.com/billing/subscriptions/usage-based/billing-credits. Modern Treasury NOT fetched (Stripe used as the allowed alternative).
- One wallet per customer: Lago docs contradictory in summary: "each customer can maintain up to 5 active wallets" (priority 1-50, 1 first) yet "each customer can only have one active wallet" currently. Lago blog: "one or more wallets (often segmented by product, region, or currency)". Stripe: customer has multiple credit grants. => design with wallet-per-currency/purpose and allow N later; don't hard-code 1.
- Immutable append-only: Lago blog "Audit logs should be immutable - stored in append-only format"; Flexprice "every credit, debit and expiration" append-only; Stripe: "A credit grant is backed by an immutable, append-only ledger." CONFIRMED.
- Lago transaction model (API list endpoint): transaction_type `inbound` (increases) | `outbound` (decreases); status `pending` | `settled` | `failed`; transaction_status `purchased` | `granted` | `voided` | `invoiced`; fields credit_amount, amount, settled_at, metadata. Wallet create: `paid_credits`, `granted_credits` (free), `rate_amount`, `priority` 1-50, `expiration_at` (WALLET-level), `invoice_requires_successful_payment`, `paid_top_up_min/max_amount_cents`, `recurring_transaction_rules`, `applies_to`. Lago blog types: "initial credit purchases, consumption events, manual adjustments, refunds, and expirations". "Refund" and "adjust" are not Lago enum values; they are blog-level concepts.
- Granted vs purchased tracked separately: Lago "Granted credits: Added instantly ... at no cost"; "Purchased credits: Added only after payment confirmation" (invoice must be `succeeded`). Lago traceability (v1.45 migration page): "Distinguishing when free (granted) vs. purchased credits are being consumed" and links outbound to funding inbound transactions; "consumptions" endpoint: "how the credits from this inbound transaction were consumed by outbound transactions".
- Consumption priority: Lago does NOT state granted-before-purchased. Documented: wallet `priority` (1-50, "1 applies first") across wallets; transaction `priority` "used to determine the order in which inbound transactions are consumed. Lower values are consumed first." Lago blog: "use-oldest-first" typical. Stripe is explicit: grant `priority` (lower number first) -> earlier `expires_at` -> `promotional` category first -> earlier effective_at -> earlier created.
- Expiry: Lago wallet-level ("all remaining credits are automatically voided" at expiration_at; default carry forward indefinitely). Stripe per grant `expires_at` (none unless set). Blog: "expiring soon" 30 days before.
- Idempotency: Lago `transaction_id` on usage events: "if the same event arrives twice, it is billed once." Postgres store key transaction_id+external_subscription_id, duplicate -> 422; ClickHouse dedup differs (200, latest replaces). Flexprice: idempotency key processes request once. Blog: "globally unique identifiers that persist across retries". CONFIRMED.
- Balance vs ongoing balance: Lago "Balance: invoiced balance"; "Ongoing Balance: real-time estimate including current usage, taxes, and draft invoices" (flagged premium feature in docs). Stripe: ledger balance vs available balance ("ledger balance less any expired credits or unrecorded transactions").
- Reservation/hold: from Lago blog ("available balance (excluding reserved amounts), reserved balance (for in-flight transactions)"; optimistic locking with version numbers) and Flexprice ("hold some credits for long running tasks") - so it IS in the sources, but as blog-level practice, not Lago's API (no reserved field in Lago wallet/transaction enums) and not Stripe.
- Stripe grants: Credit Grant has category (paid/promotional per Stripe's prepaid vs promotional use cases), `priority`, `effective_at`, `expires_at`, `applicability_config` (price-scope: only listed metered prices), states Pending/Granted/Depleted/Expired/Voided; void only if not applied; Credit Balance Transactions (credits & debits) ; limit 100 unused grants per customer; credits apply at invoice finalization; void invoice reinstates credits; credit note does NOT refund applied grants (must create new grant). Compliance note: credits can't be stored value/gift cards, cannot be spent with third parties - relevant for "free mode" wallet legality.
Design implication: model = wallet -> grants (source: purchased|granted, priority, expires_at, scope) -> append-only ledger entries (type, delta, grant_id, idempotency_key, status pending/settled/failed/voided); balance = SUM(ledger) over non-expired; reservation as separate hold entries (general ledger practice).
Newer: Lago traceability (granted vs purchased consumption visibility) and per-transaction priority.
